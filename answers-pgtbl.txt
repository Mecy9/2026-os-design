1. print_pgtbl 输出说明

本机一次运行中，前十页里 0x0、0x1000 是 pgtbltest 的用户代码页，权限
0x5b 表示 V、R、X、U、A：映射有效，用户态可读和执行，且硬件已经访问
过。0x2000 是程序的数据页，第一次打印时权限为 0x17，即 V、R、W、U；
0x3000 是栈下面的 guard page，权限为 0x07，即 V、R、W，但故意清除了 U，
所以用户态访问会产生异常；0x4000 是用户栈，0xd7 表示 V、R、W、U、A、D，
它已经被读写过。0x5000 到 0x9000 尚未映射，因此 PTE、PA 和权限均为 0。

最高地址附近，0x3fffff6000 到 0x3fffffc000 没有映射。0x3fffffd000
是 USYSCALL，共享页只给用户态读取，初次打印的 0x13 表示 V、R、U；页内
保存当前进程的 pid。0x3fffffe000 是 trapframe，保存陷入内核时的用户寄存器，
0xc7 表示 V、R、W、A、D，没有 U，用户态不能直接访问。0x3ffffff000 是
trampoline，包含用户态和内核态切换代码，0x4b 表示 V、R、X、A，同样没有
U。各次启动时物理页地址可能不同，这属于正常现象。

2. 还可以怎样利用共享页加速系统调用

最直接的是 uptime：内核把 ticks 的只读快照放在共享页中，用户库直接读取，
就不必为每次查询执行 ecall。不过 ticks 会被中断处理并发修改，实际实现不能
只复制一个裸整数；可以采用序列计数器，用户在读取前后检查版本号，版本变化就
重读。类似地，也可以把父进程 pid 等变化少、只需读取的每进程信息放在此页。
涉及文件、权限检查或会修改内核状态的调用不适合这样做。

3. vmprint 的叶子项及其与 print_pgtbl 的关系

vmprint 从 Sv39 的第 2 级页表递归到第 0 级。没有 R/W/X 的有效项只是指向
下一级页表；带 R、W 或 X 的项才是叶子。低地址一侧的叶子依次对应代码、数据、
guard page 和用户栈；高地址一侧的三个叶子依次对应 USYSCALL、trapframe 和
trampoline。它们的权限含义与第 1 问相同。vmprint 中某些 A、D 位会比早先
print_pgtbl 多，是因为两次打印之间程序已经读取或写入了相应页面，硬件据此
设置了 accessed/dirty 位。

print_pgtbl 通过 pgpte 只显示指定虚拟页的最终 PTE；vmprint 还显示从根页表
走到叶子所经过的中间 PTE，所以能看到完整的三级树结构。两者在同一虚拟地址
上的叶子映射相互对应，除运行期间可能变化的 A/D 位外，物理页和主要权限一致。
